# [39강. Mapping·Localization 데이터 흐름과 Loop Closure]
- 모듈: ⑥ SLAM 및 Nav2 자율주행
- 한 줄 요약: 37강(SLAM)·38강(필터)의 조각이 실제로 배선되는 회로도 — **`map→odom→base_link` 프레임 규약**, 매핑/위치추정 모드의 데이터 흐름, **Loop Closure의 감지·검증·교정**과 오탐의 위험
- ※ 교안에 코드 블록이 없는 이론 강의 → 이 폴더는 요약만 담음

## [필수 이해 기준 (교안 기준)]
- **필수 ①** `map → odom → base_link` 세 프레임의 역할과 각 변환의 발행자
- **필수 ②** map→base_link를 직접 발행하지 않고 **불연속을 map→odom에 격리**하는 이유
- **필수 ③** Loop Closure의 정의와 **잘못된 루프(오탐)**가 위험한 이유
- 심화(선택): 그래프 최적화의 오차 배분, 루프 검증 파라미터 — 실습에서 지도가 어긋나면 원인 대부분이 이 강의에 있음

## [핵심 개념]
- **프레임 체인** $\text{map}\to\text{odom}\to\text{base\_link}\ (\to\text{laser, camera}\dots)$
  - 각 화살표 = 좌표 변환(위치 [m] + 회전 [rad])
  - map = 지도 고정 기준, odom = 출발점 기준, base_link = 로봇 본체

  | 변환 | 성질 | 의미 | 담당 |
  |---|---|---|---|
  | odom→base_link | 연속·매끄러움, 드리프트 있음 | "출발점 기준 나" — 빠른 제어용 신호 | 오도메트리(EKF, 38강) |
  | map→odom | 불연속 점프 허용, 드리프트 없음 | "오도메트리가 얼마나 틀렸나"의 교정값 | SLAM/AMCL (이번 실습은 cuVSLAM) |

  - map 기준 위치 = map→odom ∘ odom→base_link 합성
  - cuVSLAM은 설정에 따라 두 TF를 모두 발행 가능 → 바퀴 EKF·AMCL·시뮬레이터가 **같은 연결을 중복 발행하지 않도록 프레임마다 발행자 1개** 계약
  - 직접 pose 메시지와 TF를 혼동하지 않기
- **불연속 격리 설계 — ROS 내비게이션의 핵심 결정**
  - 제어 루프는 매끄러운 위치가 필요(순간이동 시 제어 출력 폭발 — 모듈 ① 감각)
  - 전역 보정은 점프가 불가피(루프 폐합의 순간)
  - 두 요구를 한 변환에 못 담음 → 매끄러움은 odom→base_link, 점프는 map→odom에 격리
  - 실무 규칙: 속도는 **odom 기준**으로 계산 — map 기준 위치를 미분하면 점프 순간 출력이 튐
  - 교안 그림: odom 궤적(매끄럽지만 휨)과 map 궤적(참에 근접)의 차이 = map→odom 교정 화살표, 루프 폐합 순간 map→odom만 툭 점프
- **매핑 모드(41강 배선)**
  - Isaac Sim 스테레오 영상·CameraInfo(+RGB-D 깊이, 선택 IMU) → cuVSLAM: 6DoF 포즈·시각 지도·TF
  - 깊이 + 추정 포즈 → nvblox: TSDF/ESDF·메시 → nvblox_nav2: 2D 비용지도 → Nav2
  - 시뮬레이터 참값 포즈는 **평가용으로 분리**
  - LiDAR·slam_toolbox 도식은 2D 비교용일 뿐, 이번 카메라 실습의 배선 아님
- **위치추정 모드(42강 배선)**
  - 저장한 cuVSLAM 시각 지도 + `pose_hint`로 재위치 추정, nvblox 상태는 별도 로드
  - AMCL·map_server를 기본 위치 공급자로 기동하지 않음
  - 2D LiDAR 비교 구성은 map_server+AMCL로 교체 가능하나 지도 형식·센서 계약이 달라짐
  - 위치 공급자만 바뀌고 TF 규약은 유지 → 하류(Nav2)는 영향 없음
- **Loop Closure — 왜 필요한가**
  - 루프 없이 큰 건물을 한 바퀴 돌면 복귀 지점에서 **수십 cm~수 m 어긋남(이중 벽)**
  - 스캔 매칭이 지역적으로 아무리 좋아도 오차는 누적(37강)
- **3단계 과정**
  1. 감지(detection): 현재 스캔/장면을 **과거 키프레임**과 매칭 — 오도메트리상 가까운 과거 포즈가 후보
  2. 검증(verification): 매칭 품질(일치도·일관성)이 문턱을 넘어야 채택 — **안전장치**
  3. 교정(correction): 루프 엣지를 그래프에 추가 후 전역 최적화 → 오차가 **경로 전체에 부드럽게 배분**(전역 최소자승), 마지막 지점만 고치는 것이 아님
- **실패 모드 — 잘못된 루프**
  - 닮은 장소(같은 규격 복도, 반복 사무실 칸)를 같은 곳으로 오인 → 최적화가 멀쩡한 지도를 **접어 버림**(두 복도가 하나로), 회복 곤란
  - **오탐(false positive) ≫ 미탐(false negative)** 치명도: 미탐 = 어긋남 잔존(복구 가능), 오탐 = 지도 붕괴
  - "실수의 비용이 비대칭이면 문턱도 비대칭" → 검증 문턱은 보수적으로 (29강 박스 깜빡임의 등장 문턱과 같은 원리), 41강에서 문턱 파라미터 직접 조작
- **(심화) 장소 인식·루프 폐합·재위치 추정 구분**
  - 루프 폐합: 주행 중 다시 본 장소의 구속으로 궤적 보정
  - 재위치 추정: 재시작·추적 손실 후 저장 지도에서 현재 위치 찾기
  - cuVSLAM 단독의 힌트 없는 전역 위치 추정은 가정하지 않음 → 41강 VO/SLAM 궤적 비교, 42강 저장 지도+`pose_hint` 복구

## [용어]
- **map 프레임**: 지도 고정 기준 — 목표·전역 계획의 기준, 드리프트 없지만 점프 가능
- **odom 프레임**: 출발점 기준 매끄러운 좌표 — 제어·속도 계산용, 서서히 틀어짐
- **base_link**: 로봇 본체 좌표계, 센서의 부모 — base_footprint(지면 투영)와 구분하는 관례도 있음
- **map→odom**: 오도메트리 오차의 교정값 — 로봇 위치가 아니라 보정량
- **TF 트리**: 좌표계 부모–자식 구조 — 한 프레임에 부모가 둘이면 오류
- **Loop Closure**: "와 본 곳" 인식 후 누적 오차를 한 번에 펴는 장치 — 지역 교정(스캔 매칭)과 규모가 다름
- **키프레임 매칭**: 과거·현재 장면 비교로 루프 감지 — 유사 장소에서 오검출 위험
- **그래프 최적화**: 전체 궤적을 한꺼번에 조정해 오차 배분
- **거짓 루프**: 다른 곳을 같은 곳으로 오인 — 지도를 접는 참사, 검증 문턱이 중요

## [교안의 실습 과제]
- 코드 블록은 없지만 교안이 직접 해 보라고 제시한 과제
1. **TF 트리 손그림**: 매핑/위치추정 모드 각각의 TF 트리(map~센서)와 변환별 발행자 → 41·42강 `view_frames` 결과와 대조할 답안지
2. **점프 격리 시뮬레이션**: 참 궤적·드리프트 낀 odom 궤적 생성, 5초마다 전역 보정이 map→odom 갱신 → map 기준(계단식)과 odom 기준(매끄러움) 위치 나란히 그리기
3. **루프 배분 실험**: 37강 1차원 그래프 최적화 확장 — 포즈 10개 + 루프 구속 1개의 포즈별 교정량 막대그래프, 한 구간만 오도메트리 불확실성을 키우면 배분이 어떻게 쏠리는지 관찰
4. **(심화) 오탐 재현**: 실제 3 m 떨어진 두 포즈를 0 m로 잇는 틀린 루프 추가 → 전체 추정 왜곡을 수치로 확인
